# Data model

The canonical entities are shared by the client and server. Field names in TypeScript and JSON are camelCase. PostgreSQL column names are snake_case. `date` and `timestamp` are quoted because they are reserved words.

## Entities

```ts
type TransactionType = "buy-in" | "rebuy" | "cash-out";

interface Player {
  id: string;
  name: string;
  createdAt: string; // RFC 3339 timestamp assigned by the server
}

interface Transaction {
  id: string;
  sessionId: string;
  playerId: string;
  type: TransactionType;
  amount: number;    // integer greater than or equal to 1
  timestamp: string; // RFC 3339 timestamp assigned by the client
}

interface Session {
  id: string;
  date: string;      // YYYY-MM-DD
  createdAt: string; // RFC 3339 timestamp assigned by the server
  transactions: Transaction[];
}
```

On the wire, a transaction nested inside a session omits `sessionId`, because the parent supplies it. Local domain objects include `sessionId`. The OpenAPI document defines both representations.

Identifiers are 1–64 characters and match `^[A-Za-z0-9_-]+$`. UUID strings are the expected client-generated form. Player IDs use the same form and are generated by the server.

`createdAt` is not accepted in client requests. A player name is required after trimming, contains at most 80 characters, and has internal whitespace collapsed to one space.

## Local-only state

```ts
type SubmissionStatus = "draft" | "pending" | "submitted";

interface ActiveSessionRecord {
  session: Session;
  status: SubmissionStatus;
  updatedAt: string;
}
```

IndexedDB database name: `poker-tracker`.

| Store | Key | Value |
| --- | --- | --- |
| `activeSession` | constant `current` | `ActiveSessionRecord` |
| `players` | player `id` | `Player` |

The player store is a cache of the last successful server response. It can be replaced wholesale. It is not a source for creating server players.

The active-session record is the recovery source after refresh, browser restart, or failed submission. Submission status is not a database column on the server.

## PostgreSQL schema

Startup applies numbered SQL migrations and records each applied id in `schema_migrations`. Applying the same migration again is a no-op. Dates and timestamps are `TEXT`. Amounts are `INTEGER`.

```sql
CREATE TABLE players (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 80),
  created_at TEXT NOT NULL
);

CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  "date" TEXT NOT NULL CHECK ("date" ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'),
  created_at TEXT NOT NULL
);

CREATE TABLE transactions (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id),
  player_id TEXT NOT NULL REFERENCES players(id),
  type TEXT NOT NULL CHECK (type IN ('buy-in', 'rebuy', 'cash-out')),
  amount INTEGER NOT NULL CHECK (amount >= 1),
  "timestamp" TEXT NOT NULL
);

CREATE INDEX idx_transactions_session_id ON transactions(session_id);
CREATE INDEX idx_transactions_player_id ON transactions(player_id);
```

PostgreSQL enforces the foreign keys. Zod validates calendar dates, RFC 3339 timestamps, identifier syntax, and unknown player references before SQL runs. The SQL checks are a second barrier, not the only validation.

Deleting or updating a stored session is outside version 1, so foreign keys do not need `ON DELETE` behavior.

## Derived values

These values are calculated by the client and are not persisted as authoritative data.

For one player in one session:

```text
totalBuyIns = sum(amount where type is buy-in or rebuy)
totalCashOuts = sum(amount where type is cash-out)
netResult = totalCashOuts - totalBuyIns
```

For a session:

```text
sessionBuyIns = sum of every player's totalBuyIns
sessionCashOuts = sum of every player's totalCashOuts
sessionBalance = sessionCashOuts - sessionBuyIns
```

`sessionBalance` equals the sum of player net results. A non-zero balance is valid. The client must not adjust amounts to force it to zero.

Across completed sessions, a player's overall result is the sum of that player's per-session net results. Ranking sorts that overall result from highest to lowest. Equal results sort by player name using Hebrew comparison, then by player ID.

Player history walks completed sessions from oldest to newest (`date`, then `createdAt`, then `id`) and skips evenings where that player has no transactions. The cumulative result is the running sum of the remaining per-session nets. Evenings played is the length of that series, and its final value is the overall result. The results-by-session chart uses each session's `sessionBalance` in that same oldest-to-newest order. The player-comparison chart uses the ranked overall results. These views are calculated on the client and are not stored.

## Invariants

- A transaction belongs to exactly one session and one existing player.
- Amounts are positive integers. The type gives the amount its meaning.
- Transaction IDs are unique across the whole database.
- A session ID never changes during retry.
- Reusing a session ID with a different date or a different transaction set is a conflict.
- Reusing a transaction ID in another session is a conflict.
- Two transactions in one request cannot share an ID.
- Every client-side transaction in a session carries that session's ID.
- Timestamps and session dates must parse successfully. Date-only session values must not include a time.

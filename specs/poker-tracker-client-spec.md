# Poker Tracker — Client Specification

**Status:** Initial specification  
**Scope:** Client application architecture, domain model, local persistence, and server communication.  
**Out of scope:** UI/UX specification, visual design, screen layouts, and detailed interaction design.

## 1. Goals

The client is a mobile-first application used during a poker evening to record transactions for all players.

The client is responsible for:
- Maintaining the current session and its transactions.
- Saving every change locally as it happens.
- Calculating balances, profit/loss, and session statistics.
- Sending a complete session to the server when the user chooses to submit it.
- Keeping local data until the server confirms successful persistence.

The server is responsible for persistence, retrieval, validation, and data integrity. It does not calculate poker results or statistics.

## 2. Technology

- React
- TypeScript
- Vite
- IndexedDB for durable local storage
- Fetch API for HTTP communication
- CSS / CSS Modules (UI styling is defined in a separate specification)

Avoid adding state-management, data-fetching, routing, or UI libraries unless an actual requirement justifies them.

## 3. Domain model

```ts
type TransactionType = "buy-in" | "rebuy" | "cash-out";

interface Player {
  id: string;
  name: string;
  createdAt: string;
}

interface Transaction {
  id: string;
  sessionId: string;
  playerId: string;
  type: TransactionType;
  amount: number;       // Positive integer in whole currency units
  timestamp: string;    // ISO 8601 timestamp
}

interface Session {
  id: string;
  date: string;         // YYYY-MM-DD
  createdAt: string;
  transactions: Transaction[];
}
```

A session's participants can initially be derived from the distinct `playerId` values in its transactions. The model may be extended later if attendance without a transaction needs to be represented.

IDs are generated by the client. A session ID remains stable across retries of the same submission.

## 4. Client-side responsibilities

### 4.1 Session management

- Start a new session with a stable ID and session date.
- Add transactions to the active session.
- Edit or delete transactions before submission.
- Load players from the server and allow the user to select a player for a transaction.
- Keep the active session available after refresh, browser restart, or temporary loss of connectivity.

### 4.2 Calculations

All poker-specific calculations are performed by the client.

At minimum, the client should be able to calculate per player:
- Total buy-ins (`buy-in` + `rebuy`).
- Total cash-outs.
- Net result: total cash-outs minus total buy-ins.

The client may also calculate session-level totals and other statistics. These are derived values and are not persisted as authoritative server data.

### 4.3 Local persistence

Use IndexedDB rather than relying only on in-memory state or `localStorage`.

Persist:
- The active session and its transactions.
- Submission state.
- Any local metadata needed to recover an interrupted session.

A transaction must be persisted locally before the UI treats the recording operation as complete.

Suggested local submission states:

```ts
type SubmissionStatus = "draft" | "pending" | "submitted";
```

- `draft`: session is still being recorded.
- `pending`: user requested submission, but the server has not yet confirmed it.
- `submitted`: server confirmed successful persistence.

Do not delete the local session immediately after sending it. Retain it until a successful server response is received. After confirmation, the client may retain it as a local submitted copy or remove it according to a later retention policy.

## 5. Server communication

The client communicates with the server through a small API layer. Components and domain logic should not call `fetch` directly.

### 5.1 API operations

| Operation | Endpoint | Purpose |
|---|---|---|
| List players | `GET /api/players` | Load players available for transactions |
| Create player | `POST /api/players` | Add a player |
| Submit session | `POST /api/sessions` | Submit a complete session and all its transactions |
| Get session | `GET /api/sessions/{id}` | Retrieve a complete session |
| List sessions | `GET /api/sessions` | Retrieve sessions, optionally filtered by date |

The detailed HTTP contract, request/response schemas, and error format should be defined in a separate **OpenAPI 3.1** document. The client should use that document as the source of truth for the API contract.

### 5.2 Session submission

The client submits one complete session object, including all transactions, in a single request.

Expected flow:
1. Persist the latest session locally.
2. Mark it `pending`.
3. Send the complete session to `POST /api/sessions`.
4. If the server confirms success, mark the local session `submitted`.
5. If the request fails or the result is uncertain, keep it `pending` and allow retry.

The server must treat the session ID as an idempotency key:
- Retrying the same session must not create duplicate records.
- Reusing the same session ID with different content must return a conflict (`409`).

The client must not create a new session ID when retrying a submission.

### 5.3 Error handling

The API layer should distinguish:
- Network or connectivity failures.
- Validation errors (`400`).
- Missing resources (`404`).
- Conflicts (`409`).
- Unexpected server errors (`500`).

A failed submission must never cause the local session or its transactions to be discarded.

```text
  features/

```

This is a starting point, not a requirement to create every folder immediately. Keep domain calculations independent of React and persistence.

## 7. Validation and invariants

Validate data before submission, even if the server validates it again.

- IDs must be present and stable.
- Transaction type must be one of the supported values.
- Amount must be a positive integer.
- Every transaction must reference the current session ID.
- Every transaction must reference a known player.
- Timestamps must be valid ISO 8601 values.
- Session date must use `YYYY-MM-DD`.

The server remains authoritative and may reject invalid data.

## 8. Non-goals for this phase

- Multi-user live editing or synchronization.
- Real-time updates between multiple devices.
- Offline access to the full historical session library.
- Server-side poker calculations or analytics.
- Image generation or other AI features.
- UI layout, styling, and detailed mobile interaction design (covered by a separate UI specification).

## 9. Open decisions

These can be decided when implementation requires them:
- Whether submitted sessions remain in IndexedDB indefinitely or are removed after a retention period.
- Whether the client should support editing a session after server submission.
- Whether player creation is allowed during an active session when offline.
- Whether a separate attendance model is needed for players who attend but make no transaction.
